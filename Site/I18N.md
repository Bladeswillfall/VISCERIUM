# Internationalisation readiness

VISCERIUM is currently published in English. The Codex has an internationalisation foundation without creating a translation or locale-routing obligation before a second language is commissioned.

## Current contract

- English remains the canonical and only required published locale.
- The configured public locale is the BCP 47 tag `en-GB`, exported as `DEFAULT_LOCALE` from `site.config.mjs`.
- Starlight's native `i18n` content collection owns interface messages. The default catalogue is `src/content/i18n/en-GB.json`.
- Astro components read messages through `Astro.locals.t`. Do not add a parallel dictionary or a global client translation runtime.
- Client islands receive only the locale, direction, and messages they need in their existing serialised payload or `data-*` attributes.
- Dates, numbers, plural rules, and lists use `Intl` through the helpers in `src/lib/i18n.mjs` or a component's local formatter.
- Layout and interaction code uses logical directions where direction matters. Keyboard navigation must respect the rendered `dir` value.
- Canonical lore identity must not depend on a translated title. Preserve stable slugs and `entity_id` values when content is translated.
- Fictional terms do not need fabricated real-world language tags. Mixed-language source material should retain explicit language metadata when it is known.

## Dormant translation roadmap

`src/lib/i18n-roadmap.mjs` records translation intent without enabling translated routes or language controls.

- English (`en-GB`) is the published source catalogue.
- French (`fr-FR`) and German (`de-DE`) are dormant placeholders. Their placeholder message sets mirror every current `viscerium.*` interface key with `null` values so untranslated work stays explicit.
- Spanish, Chinese, and Russian are the next planned language priorities after French and German.
- The roadmap module is not imported by production pages. Starlight still sees only the English catalogue in `src/content/i18n/`.
- The French and German region tags are provisional until publication requirements are agreed. Chinese must also choose the required script and regional form before a published catalogue is created.
- `CodexHeader.astro` deliberately mounts no language selector. This prevents Starlight's native `LanguageSelect` from appearing automatically when a second locale is configured.
- `CodexLanguageMenu.astro` stores the reviewed future interaction. It is not imported by the live header. The component uses the staged Material Icon Theme `public/icons/i18n.svg` trigger and a disclosure panel of ordinary language links.
- The staged language rows use local full-colour flag SVGs only as visual shortcuts. The written language name, `lang`, `hreflang`, and `aria-current` carry the meaning for assistive technology. A flag must only be used when the published locale specifies that region.
- The component accepts complete destination URLs rather than deriving locale prefixes. When the feature is activated, pass Starlight's authoritative localized route URLs into it so the Codex does not duplicate Starlight routing rules.

Do not move a placeholder into `src/content/i18n/` until its catalogue is complete and the locale is approved for publication.

## What belongs in the interface catalogue

Put reusable chrome, control labels, accessibility text, empty states, errors, and formatter templates in the catalogue. Starlight-owned controls should use Starlight's existing keys where one already exists.

Editorial copy belongs in translated content, not in the interface catalogue. This includes article text, primers, landing-page narratives, fictional descriptions, and proper names. Calendar and map data that carries authored lore follows the same rule.

When interpolating authored text in an Astro attribute, pass `interpolation: { escapeValue: false }`. Astro performs the final HTML escaping. Client helpers must escape text before inserting HTML.

## Adding a second published locale

Locale-prefixed routing is deliberately deferred. Do not add locale folders, automatic language detection, or redirects while `en-GB` is the only published locale.

Once a second locale is approved:

1. Add its BCP 47 entry to Starlight's `locales` configuration and create a complete `src/content/i18n/<locale>.json` catalogue.
2. Add translated documents under the locale folder expected by Starlight, preserving canonical `entity_id` values and stable source relationships.
3. Build the `CodexLanguageMenu` options from Starlight's localized route data, pass localized trigger and panel labels, and mount the component immediately after Reader Settings in `CodexHeader.astro`. Keep Starlight responsible for page language, direction, fallback behaviour, and alternate-language metadata.
4. Add output tests for both the default and prefixed routes, including `lang`, `dir`, canonical and alternate links, feeds, and island payloads.
5. Test every language row with pointer, keyboard, and screen-reader navigation. Confirm that Escape returns focus to the trigger, the current language exposes `aria-current="page"`, decorative flags have empty alternative text, and each row remains at least 48 CSS pixels high.
6. Test long translated labels and the real target direction at desktop and mobile widths before publishing.

Any automatic redirect or browser-language policy requires a separate explicit product decision. The default English URL must remain directly reachable.

## Regression checks

- `tests/i18n.test.mjs` checks the configured default, catalogue completeness, dormant French and German placeholder coverage, the staged but unmounted flag language menu, fallback behaviour, formatter output, and guards against reintroducing fixed English locale calls.
- `tests/i18n-output.postbuild.mjs` checks generated HTML, timeline and map payloads, and feed language metadata after the production build.
- Browser tests exercise translated-length labels, RTL direction, and interactive controls without introducing a second public route.

## Non-goals

- Translating the current Codex as part of infrastructure work.
- Adding locale folders before a second locale exists.
- Duplicating canonical lore in multiple vault trees.
- Treating machine translation as canonical content.
- Adding a second client-side i18n framework.
